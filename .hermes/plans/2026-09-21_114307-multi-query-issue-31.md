# multi_query Implementation Plan (Roslynk #31)

> **For Hermes:** Implement task-by-task with subagent-driven-development, or execute directly.

**Goal:** Add a read-only `multi_query` MCP tool that executes several read-only Roslynk operations in a single round trip, returning one result per operation in request order.

**Architecture:** Refactor each read-only tool into a thin MCP entry point (which acquires the instance and model) plus a core that **takes the `SolutionModel` and `RoslynInstance` as parameters and never acquires them itself**, then have `MultiQueryTool` resolve each operation against an explicit static catalog of those cores and invoke them against a single `SolutionModel` captured once at the start of the batch. Results are returned in a GUID-delimited envelope (MIME-multipart style): the main header carries a fresh per-request boundary and slots are separated by it. **Boundary format decision (author): hyphens stripped** — `Guid.NewGuid().ToString("N")` gives 32 hex chars, no separators needed. **The catalog is exactly the 11 pure snapshot reads** — `get_diagnostics` and `get_solution_status` are excluded (author decision), so the pinned-snapshot guarantee is absolute with no exceptions to document or test. Argument binding is one shared reflective binder over each core's `MethodInfo` — zero per-tool binder code, drift structurally impossible.

**Tech stack:** C# / .NET, ModelContextProtocol SDK (`[McpServerToolType]` / `[McpServerTool]`), xUnit.

## Decisions (all settled with the author — see the Decisions log at the end)

1. **Over-limit ops → truncate, never reject. Author-confirmed (reverses an earlier reject decision), and deliberately the same rule as the output budget in Decision 5.** A batch of 30 ops executes ops 1–25 for real; ops 26–30 each get a whole `error=Truncated` slot and the envelope header carries `truncatedSlots=5`. Nothing is silently dropped — every requested op has a numbered slot saying either its result or why it has none.

   **The driving requirement (author): the caller must be able to continue.** Having done the first 25, the agent resends only the ops that came back `Truncated` — it never repeats work it already has. This is what makes truncation strictly better than rejection here: rejection throws away a well-formed request and forces the caller to re-plan the split itself, while truncation answers as much as it can and hands back an exact, mechanical continuation list.

   For this to work the envelope must make the continuation trivially derivable, which the slot framing already guarantees: every truncated slot keeps its **original 1-based index** and its **tool name** on the `slot=` meta line, so "resend the ops whose slots were `Truncated`" needs no bookkeeping on the caller's side beyond reading the envelope. Both limits (op count, output size) produce this identical shape — one concept for the caller to learn, one code path to test.

   **Continuation is not transactional, and Decision 8 is what keeps that honest.** The pinned snapshot dies with the call, so a continuation runs against whatever generation is current when it arrives. Read Decision 8 before implementing this one — on its own, this decision would ship a silent inconsistency.
2. **Slot framing is a per-request GUID delimiter (author's choice), hyphens stripped.** The main header carries `boundary=<32-hex>`; each slot opens with `--<boundary>` + a `slot=<i> tool=<name>` meta line; the envelope ends with `--<boundary>--`. Chosen over length-prefixed framing for skimmability (structure visible to humans/LLMs reading the transcript) and MIME familiarity. Safety does not rest on collision odds: the boundary is generated fresh per request from `Guid.NewGuid()` (v4, CSPRNG-backed, never reused or persisted), so no prior content can contain it — and the batch's pinned snapshot means nothing that *sees* the boundary can enter the slot bodies either. The two properties that make this sound (per-request freshness + pinned snapshot) are already core design commitments. Belt-and-braces: after assembly the envelope does one occurrence check. **The counted token is the delimiter line prefix `"\n--" + boundary`, not the bare 32-hex boundary** — spelling this out matters, because the `boundary=<32-hex>` header line contains the hex but not the `--` prefix, so counting the bare hex would give `n+2` and counting the prefix gives `n+1` (n slot delimiters, plus the terminator `--<boundary>--`, which starts with the same prefix). Expected count is exactly `n+1`; a mismatch is an envelope bug and faults the whole call loudly (restoring the loud-failure property length framing had, without per-slot counting). The splitter and the counter both tolerate a trailing `\r` on the delimiter line, since slot bodies can carry CRLF source text.
3. **Op item schema is self-describing**: `record MultiQueryOperation(MultiQueryOp Tool, IReadOnlyDictionary<string, JsonElement>? Arguments = null)` where `MultiQueryOp` is an enum of **exactly the 11 permitted tool names** (author's choice — the alternatives, a 22-name enum or a plain `string`, were considered and rejected; see Decision 4). The published schema therefore advertises the legal op set precisely: nothing a caller can express is ever refused as forbidden. Argument names are "exactly the corresponding single tool's parameters" (stated in the tool Description, enforced by the shared binder).

   Two mechanical requirements, both easy to get wrong and both pinned by a test:
   - **The enum must carry `[JsonConverter(typeof(JsonStringEnumConverter))]`.** No tool parameter in this repo uses an enum today, so there is no precedent to inherit: without the converter, `System.Text.Json` serializes members as **integers** and the published schema becomes `type: integer` — callers would have to send `{"tool": 4}`. Task 4 asserts the published `operations.items.tool` schema enum contains the literal string `"get_symbol"`; that assert is the entire protection.
   - **Enum member names duplicate each tool's `public const string <Tool>Name`.** A C# identifier may legally be `get_symbol`, but the duplication is a new drift channel. Task 3's resolution test asserts: enum member-name set == catalog `ToolName` set == the 11 tool-name constants, and that every *other* `[McpServerTool]` name in the assembly is absent from the enum (so a newly added tool is never silently admitted).
4. **A tool outside the 11 is refused at argument binding, as a whole-batch `error=Invalid`** — author's choice, and the direct consequence of the 11-name enum in Decision 3. `"rename_symbol"` is not a representable enum value, so the MCP SDK rejects the call before `MultiQueryTool` runs; `RoslynkTool` maps that to the standard header-only `error=Invalid`, whose message carries the property name and the permitted values.

   Consequences, accepted deliberately:
   - **There is no `RejectedOps` map and no slot-level `NotSupported` path.** Forbidden names cannot reach the server, so classifying them server-side would be dead code. The catalog is the single list.
   - **One forbidden op fails the entire batch**, rather than yielding one error slot beside 19 good results. Acceptable because the schema tells the caller the legal set up front — sending a write tool is a caller bug the schema already prevents, not a runtime condition to degrade gracefully around.
   - **The issue's "write tools rejected with `NotSupported`, naming the offending op" is satisfied in substance, not in letter**: the rejection names the offending value and the permitted set, but as `Invalid` at batch level rather than `NotSupported` per slot. The acceptance table records this deviation explicitly; raise it with the issue owner if the letter matters.

   Rejected alternatives: a 22-name enum (every tool representable, forbidden ones answered per-slot with `NotSupported`, at the cost of a schema advertising 9 names that always fail) and a plain `string` (same per-slot behavior, but the schema stops advertising the op set at all).
5. **Response-size budget — the second truncation trigger, same mechanism as Decision 1.** A batch of 25 ops × `find_references` (default 100 results) can produce an enormous single response — worse for an agent than 25 calls. Total output is capped at `MaxTotalOutputChars = 200_000`. Ops run whole, in order; after each one the accumulated total is compared to the cap, and once it is crossed every *remaining* slot becomes an `error=Truncated` block with `truncatedSlots=<n>` on the header — byte-identical in shape to an op-count truncation, so the caller's continuation logic is the same either way.

   **A slot body is never cut mid-output.** That would break the "slot bodies are the tool's existing output, verbatim" contract and can leave a half-written tab-indented leaf no parser can read — and it would also break continuation, since a caller cannot tell a partial answer from a complete one. There is no `truncated=Y` marker: a slot is either its complete real body or a complete `Truncated` error block, never a fragment. One consequence, accepted deliberately: a single op whose own output exceeds the cap still ships whole (it is the first slot to cross the line, not the first to be refused), so the cap bounds overshoot to one op's output rather than enforcing a hard ceiling.

   **Naming collision to avoid — `find_references` already emits its own `truncated=Y` and `count=` headers** when it caps its result list (see `FindReferencesTests.cs:51`). That is a *tool-level* marker inside a slot body and is unrelated to batch truncation. Keep the two vocabularies distinct — the envelope uses `truncatedSlots=<n>` and `error=Truncated`, never a bare `truncated=` — and never assert on a bare "truncated" substring across a whole envelope, since a legitimate `find_references` body can contain it.

   **Message text must serve the continuation**: `error=Truncated` / `errorMessage=response budget exhausted after N operations; resend the remaining operations` (and, for the op-count case, `at most 25 operations per batch; resend operations 26-30`). The caller should not have to infer what to do next.

   `Error.Truncated` **does not exist today** — `Infrastructure/Results/Error.cs` provides `Indexing`, `Faulted`, `NotFound`, `Ambiguous`, `NotSupported`, `Stale`, `Invalid`, `Conflict`. Task 2 adds the factory and code (and checks whether the skill's error-code list needs the new entry). Reusing `Invalid` is no longer a sensible fallback now that truncation is the behavior for *both* limits: it is a routine, expected, continuable outcome rather than a caller error, and it deserves its own code.
6. **No envelope-level `status=` header** — every slot body already carries its own `status=` line when the solution isn't Ready (OutlineBuilder convention), so a duplicate at the envelope level is noise. Whole-batch failures (`Indexing` etc.) are formatted with the model's status as usual.
7. **Pinning is eager and uniform**: `solutionId` is required at batch level, and a batch issued while the referenced solution is still loading returns whole-batch `Indexing` — identical to every other tool. With `get_solution_status` excluded (Scope decision 2), every catalogued op genuinely needs the solution, so there is no longer any case where the requirement is arguably over-strict. Documented in the Description.
8. **Continuation across calls is checkable, not assumed — snapshot identity (author's choice).**

   Decision 1's continuation pattern has a hole that must be closed rather than papered over: **the pinned snapshot does not survive the call.** `SolutionModel` is pinned only for the duration of one batch; nothing holds it afterwards, so a continuation call takes a fresh `ReadModelAsync()` and gets whatever is current then. If anything wrote in between — another MCP client, or simply the user saving a file, since `SolutionFileSync` watches disk — run 2's slots describe a different generation than run 1's. The batch guarantee is therefore *per run*, never across runs, and without a marker the seam is **undetectable**: an agent holding 30 slots from two envelopes has nothing telling it that slots 1–25 and 26–30 may disagree.

   The fix is to make the seam loud:

   - **`SolutionModel` gains `public Guid Id { get; init; } = Guid.NewGuid();`** — one line. The type is already immutable and swapped atomically by `RoslynInstance.Swap`, so every published generation gets a distinct identity for free. This is the plan's only lifecycle change, and it adds no locking, no allocation on the read path, and no behavior.
   - **Every multi_query envelope carries `snapshot=<guid>`** in its header, naming the generation all its slots were computed against.
   - **Header-only failures carry no `snapshot=`, with one exception — `Stale`.** The rule follows from what actually exists at the point of failure:

     | Failure | Model pinned? | `snapshot=` |
     |---|---|---|
     | Structural `Invalid` (empty list, malformed item) | no — fails before pinning | none exists |
     | Binding `Invalid` (tool outside the enum) | no — the SDK rejects before the tool runs | none exists |
     | `Indexing` | pinned, but `model.Solution` is null | none exists |
     | `Stale` | pinned | **emit `snapshot=<current id>`** |
     | `Faulted` (integrity check) | pinned | skip — a server bug, nothing the caller can act on |

     `Stale` emits the *current* id as a real header, not only inside `errorMessage=`, because `errorMessage=` is free text and an agent should not have to regex a sentence for two GUIDs. This follows existing convention rather than inventing a shape: `NotFound` already carries structured `candidate=` lines beside `error=`/`errorMessage=`. The message still names both the expected and the current id in prose for a human reading the transcript.
   - **`multi_query` gains an optional `expectSnapshot` parameter.** When supplied and it does not match the pinned model's `Id`, the whole batch is refused with **`error=Stale`**, whose message names the expected and current ids and says to re-run the full batch rather than stitch generations. When omitted, nothing changes — the check is opt-in, so an ordinary one-shot batch is unaffected.

   `Error.Stale` currently requires a `staleFiles` list (`Error.cs:30`). Either add an overload without it or pass `[]`; the code is the right one — this is precisely the existing "the world moved under you" condition the write tools already report, and reusing it means agents need no new concept.

   **Known and judged irrelevant: a diagnostics build can mint a new id without the code changing.** `RunDiagnosticsAsync` publishes `Loading(solution)` then `Ready(solution)` around a build (`RoslynInstance.cs:258-262`), passing the *same* `Solution` object both times. With the id on `SolutionModel`, those swaps produce new ids although the source is identical, so a continuation that straddles such a build is refused as `Stale` when nothing actually changed.

   This is accepted, not overlooked. The window is narrow — it needs a cache-*miss* diagnostics build (a cache hit swaps nothing) to land between a truncated batch and its continuation, and every other cache-invalidating event is a real change that *should* produce `Stale`. `get_diagnostics` is not batchable, so it can only arrive as a separate call or via the watcher's auto-diagnostics, which follows a genuine write anyway. And the consequence is benign in the safe direction: the caller re-runs the whole batch and gets correct, mutually consistent results. A false `Stale` costs work; it never returns wrong data.

   Do **not** "fix" this by loosening the check to compare `model.Solution` reference identity instead — that makes the header name one thing and the check test another. If it ever proves a nuisance in practice, the clean change is to key the published id off the `Solution` object itself (a `ConditionalWeakTable<Solution, string>` in the multi_query feature), which is exact by construction and removes the `SolutionModel` change entirely. Not worth doing pre-emptively.

   **The caller keeps its own op list.** Slot meta lines carry the original 1-based index and tool name, never the arguments, so a continuation is built from the caller's copy of the request — the server does not echo the ops back and cannot reconstruct them. Say this in the tool Description and the skill, or an agent will expect a resumable handle it never got.

   **Do not "improve" this by echoing each truncated op's arguments back**, tempting though a self-contained response looks:
   - in the **budget** case it is perverse — it spends the response budget that just ran out on re-transmitting the caller's own input;
   - in the **op-count** case it is pure duplication of a request the caller sent milliseconds ago and still holds;
   - it invites agents to treat the response as a resumable handle. Nothing is held server side; that is precisely why `expectSnapshot` exists.

   Index plus tool name is the right amount of information: enough to identify *which* ops are missing, without pretending to be a transaction log.

   What this buys, stated plainly: continuation remains **best-effort, not transactional**. The server does not keep old snapshots alive (that would mean statefulness, pinned Roslyn `Solution` graphs, TTLs and eviction — rejected for v1, and a continuation minutes later returning deliberately stale code is arguably worse than fresh). What `expectSnapshot` guarantees is that a caller who continues either gets a genuinely consistent union or is told, loudly, that it cannot have one.


## Scope decisions (resolved against the issue text)

1. **In scope for v1 — the 11 pure snapshot reads:** `get_symbol`, `get_symbol_body`, `get_members`, `find_definition`, `find_implementations`, `find_references`, `get_callers`, `search_symbols`, `get_type_hierarchy`, `find_dead_code`, `find_dead_conditionals`. Every one runs entirely on the pinned `SolutionModel`, so the batch's consistency guarantee is absolute and unqualified.

   **The membership rule (author's, and the one to apply to any future tool): a multi_query op describes the source.** It answers "what is this code" against a fixed snapshot. Two kinds of tool fail that test and are excluded no matter how read-only they look — tools that report *server* state rather than source (`get_solution_status`), and tools that are a *precursor to changing* the source (`get_code_actions`). `get_diagnostics` is excluded for the separate mechanical reason in Scope decision 2.

   **Deliberate delta from the issue's tool list:** the issue names 11 tools; this catalog is that list minus `get_diagnostics` and `get_solution_status`, plus `find_definition` and `find_implementations`. The two additions are not in the issue but satisfy the membership rule exactly — both are pure snapshot reads that describe the source, and both are natural batch companions to `get_symbol`/`find_references`. Recorded here so a reviewer sees the addition as intentional. Mention it in the PR description alongside the two removals.
2. **Not multi-queryable** — none of these is representable in the `MultiQueryOp` enum, so each is refused at argument binding as a whole-batch `error=Invalid` (Decision 4):
   - **`get_diagnostics` and `get_solution_status` — excluded by author decision**, though the issue lists them. They are the only two tools that do not read the pinned snapshot: `get_diagnostics` goes through `instance.RequestDiagnosticsAsync` (fences writes, may compile, can return a newer solution generation than the pinned one) and `get_solution_status` is registry-wide and takes no `solutionId` at all. Admitting either would mean shipping a consistency guarantee with documented exceptions; excluding them keeps the contract absolute. Both remain available as ordinary single calls, which is how an agent should use them — `get_diagnostics` in particular is the write/verify loop's tool, not a query to batch alongside symbol lookups.
   - Write tools (the 6 `ReadOnly = false` tools) — the issue says writes are a separate concern.
   - `get_code_actions` — **it is a precursor to making a change**, not a description of the source: you call it to find out which fix to execute. Everything in the catalog answers "what is the code"; `get_code_actions` answers "what could I do to it", which belongs with the write path, not a read batch. (The earlier draft justified this as "not in the issue's tool list" — that was wrong twice over, since `find_definition` and `find_implementations` are not in the issue's list either.)
   - `open_solution`, `reload_solution` — `ReadOnly = true` in the MCP sense but they start loads / mutate instance state; a multi_query must be a pure read against the solution.
3. An empty op list → whole-batch `error=Invalid`; an oversized one truncates rather than failing (Decision 1). Per-op `solutionId` → rejected as an unknown argument (no core declares one).

## Proposed shape

```jsonc
// Request — one call
{
  "solutionId": "C:/path/to/MySolution.slnx",
  "operations": [
    { "tool": "get_symbol",      "arguments": { "symbolName": "MyLib.Ledger" } },
    { "tool": "get_members",     "arguments": { "typeName":   "MyLib.Ledger" } },
    { "tool": "find_references", "arguments": { "symbolName": "MyLib.Ledger", "maxResults": 200 } }
  ]
}
```

```text
# Response — one result per operation, in request order
operations=3
snapshot=3d9b17c0f4e2426fa1b8e0d7c5a94612
boundary=7f3a9c2e4b1d4f8a9e6ca2d5f8b1c3e7

--7f3a9c2e4b1d4f8a9e6ca2d5f8b1c3e7
slot=1 tool=get_symbol

resolvedSymbol=MyLib.Ledger
… (the tool's existing output format, verbatim)

--7f3a9c2e4b1d4f8a9e6ca2d5f8b1c3e7
slot=2 tool=get_members

…

--7f3a9c2e4b1d4f8a9e6ca2d5f8b1c3e7
slot=3 tool=find_references

error=NotFound
errorMessage=No symbol matched 'MyLib.Ledger'.
candidate=MyLib.Ledgers

--7f3a9c2e4b1d4f8a9e6ca2d5f8b1c3e7--
```

> **Argument names are each single tool's real parameter names — copy them from the tool file, never from memory.** The example above is the trap in miniature: `get_symbol` takes `symbolName` but `get_members` takes **`typeName`** (`GetMembersTool.cs:59`), and under the strict binder a `symbolName` there is an unknown argument → slot `Invalid`. Likewise `find_definition` is position-based (`filePath`, `line`, `column`), not symbol-based. The same worked example is copied into `SKILL.md` in Task 6 and into the Task 2/3 tests, so an error here propagates to three places.

- `operations=<n>` header first, then `snapshot=<32-hex>` (the `SolutionModel.Id` every slot was computed against — pass it back as `expectSnapshot` to continue a truncated batch safely, Decision 8), then `boundary=<32-hex>` (fresh per request, `Guid.NewGuid().ToString("N")` — hyphens stripped per the author's call; add `truncatedSlots=<n>` when either limit bit — op count or output budget). Each slot opens with a `--<boundary>` delimiter line, then one meta line `slot=<i> tool=<name>`, a blank line, then the op's existing output — success or failure, unchanged and never truncated mid-body (Decision 5). The final `--<boundary>--` (trailing dashes) terminates the envelope, MIME-style. Slot content cannot contain the delimiter because the boundary is generated fresh per request and the batch runs on a pinned snapshot (Decision 2).
- A failing op yields its normal `error=` block in its own slot and does not abort the batch — whether it *returns* an error, *fails to bind*, or *throws* (Design C step 4).
- **Structural rejections are whole-batch `error=Invalid`** (empty list, an op that isn't an object, missing `tool` key) — the batch cannot be interpreted at all. An op count over 25 is *not* in this list: it truncates (Decision 1). Over the wire, an unknown `tool` value is normally caught earlier by the enum schema as a binding-level Invalid; the catalog-miss branch is the defensive in-server fallback.
- **Unknown `arguments` keys, missing required arguments, or wrong-typed values** → `error=Invalid` in that op's slot, naming the op index, the tool, and the parameter — never silently ignored.
- **No `maxOperations` parameter** — the limit (25) and the output budget are server-side constants. YAGNI.

## Design

### A. The entry/core split (per tool)

Current shape (GetCallersTool.cs:55-102 is the canonical example):

```csharp
[McpServerTool(...)]
public async Task<string> GetCallers(string solutionId, string methodName)
{
    RoslynInstance instance = await InstanceRegistry.GetOrBeginAsync(solutionId);
    SolutionModel model = await instance.ReadModelAsync();
    // ... body works on model ...
}
```

Target shape — **no shared pinning helper** (each entry keeps its own two acquisition lines; they were already identical and there is no duplication worth a cross-feature delegate), and — critically — **acquisition stays in the entry, never in the core**. The core takes the model and instance as parameters. This is the whole seam: a core that calls `ReadModelAsync` itself would give each op in a batch its own snapshot and destroy the consistency guarantee, and `ExecuteBatchAsync(pinnedModel, …)` (Task 5) would have nothing to pass it to.

```csharp
[McpServerTool(...)]   // attributes + Description stay verbatim on the entry
public async Task<string> GetCallers(string solutionId, string methodName)
{
    RoslynInstance instance = await InstanceRegistry.GetOrBeginAsync(solutionId);
    SolutionModel model = await instance.ReadModelAsync();
    return await GetCallersCoreAsync(model, instance, methodName, CancellationToken.None);
}

internal async Task<string> GetCallersCoreAsync(
    SolutionModel model, RoslynInstance instance, string methodName, CancellationToken token)
{
    // ...same body, minus the two acquisition lines...
}
```

Two rules that fall out of this and apply to every one of the 11:

- **The `model.Solution is null` → `Error.Indexing()` pre-check belongs in the core**, not the entry. multi_query pins once and does not re-check per op, so a core invoked with a still-loading model must guard itself. (In practice the batch is rejected whole at Design C step 3, but the core must not depend on that.)
- **Token forwarding:** an entry that has no `CancellationToken` parameter today passes `CancellationToken.None`; the three that do (`GetSymbol`, `GetSymbolBody`, `FindReferences`) forward their own SDK-bound token. No entry's published signature changes.

Per-tool notes (from reading each body):

- **GetCallersTool, FindDeadCodeTool, FindDeadConditionalsTool, GetMembersTool, GetTypeHierarchyTool, FindImplementationsTool, FindDefinitionTool, SearchSymbolsTool**: bodies use only `model` + injected services; clean mechanical split.
- **GetSymbolTool, GetSymbolBodyTool, FindReferencesTool** take a `CancellationToken` parameter — thread it through the core.
- **GetDiagnosticsTool and GetSolutionStatusTool are not touched at all** — excluded from the catalog (Scope decision 2), so they keep their current single-method shape. No entry/core split, no `null!` placeholder parameters, no unused-parameter uniformity hack. This is the second simplification the exclusion buys, after the unqualified guarantee in Design D.

### B. The catalog (`MultiQueryCatalog.cs`) — explicit allow-list, shared reflective binder

```csharp
internal sealed record OpEntry(
    string ToolName,
    Type ToolType,          // the tool class, constructed via ActivatorUtilities per McpToolsRegistration.Resolve
    string CoreMethod);     // the internal core method name; MethodInfo + parameters resolved once (static readonly)
```

No `OpClass` — every catalogued op is a pinned pure read (Design D), so the classification has nothing left to distinguish.

An explicit hand-written list — never reflection over `[McpServerToolType]` (a deliberate, documented subset; reflection would silently widen it the day a future tool is marked `ReadOnly=true` but isn't solution-read-only, and would immediately readmit the two tools the author excluded). Auditability is untouched: 11 lines, one per tool.

**One shared reflective binder** (not 11 hand-written ones — with every user parameter being `string`/`string?`/`bool`/`int`, per-tool binder code is pure overhead and its drift is the failure mode an alignment test exists to catch; a generic binder makes drift structurally impossible):

```csharp
internal static async Task<string> InvokeCoreAsync(
    OpEntry entry, object tool, SolutionModel model, RoslynInstance instance,
    IReadOnlyDictionary<string, JsonElement> arguments, CancellationToken token)
{
    MethodInfo core = entry.CoreMethod resolution (cached);
    ParameterInfo[] parameters = core.GetParameters();
    var args = new object?[parameters.Length];
    var bound = new HashSet<string>(StringComparer.Ordinal);

    for (int i = 0; i < parameters.Length; i++)
    {
        ParameterInfo p = parameters[i];
        // The pinned model and its instance are supplied by the batch, never by the caller's arguments -
        // this is the line that makes the snapshot guarantee real, and it only works because Design A
        // moved acquisition out of the cores and into the entries.
        if (p.ParameterType == typeof(SolutionModel) || p.ParameterType == typeof(RoslynInstance)) { args[i] = p.ParameterType == typeof(SolutionModel) ? model : instance; continue; }
        if (p.ParameterType == typeof(CancellationToken)) { args[i] = token; continue; }

        if (!arguments.TryGetValue(p.Name!, out JsonElement value))
        {
            if (!p.HasDefaultValue)
                throw new ArgumentException($"Missing required parameter '{p.Name}' for '{entry.ToolName}'.");
            args[i] = p.DefaultValue;   // declared C# default, honoured exactly
            continue;
        }
        args[i] = Coerce(p.ParameterType, value, entry.ToolName, p.Name!);   // string→GetString, bool→GetBoolean, int→GetInt32 (or int.Parse of a string)
        bound.Add(p.Name!);
    }

    foreach (string key in arguments.Keys)
        if (!bound.Contains(key))
            throw new ArgumentException($"'key' is not a parameter of '{entry.ToolName}'.");

    return await (Task<string>)core.Invoke(tool, args)!;
}
```

The exception→`Error` mapping for per-op failures is factored out of `RoslynkTool.ToErrorResult` into a shared helper (same class or `MultiQueryExceptionMapper`): ArgumentException/FormatException/JsonException/NotSupportedException → `Error.Invalid`, else `Error.Faulted`, `OperationCanceledException` propagates. `RoslynkTool` keeps its behavior (formats with `Ready` — it has no model); the per-op boundary formats with the **pinned** `model.Status`, so a slot error during Building still carries its status header.

**Single resolution test replaces the elaborate alignment sweep:** for each catalog entry — the `CoreMethod` resolves on `ToolType` with the expected internal visibility, and its bindable parameter names (minus model/instance/token) equal the published single-tool's schema property names minus `solutionId`. One test, permanent.

### C. Execution model (`MultiQueryTool`)

1. **Validate structure** of `operations` (a non-empty array of well-formed items) → whole-batch `error=Invalid` only when the batch cannot be interpreted at all (empty list, an item that is not an object). An op count above 25 is **not** a structural failure: ops 1-25 execute and the rest become `Truncated` slots (Decision 1). Any `tool` outside the 11 enum names never reaches this point: the SDK binding layer rejects it, wrapped by `RoslynkTool` into `error=Invalid` (Decision 4). A defensive catalog-miss branch remains for the internal seam only — it records slot-level `NotFound` with the supported names as candidates, and is unreachable over the wire by construction.
2. **Pre-bind** every op's arguments through the shared binder against its catalog entry, before anything executes → slot-level `Invalid` on binder failure. Parse-all-then-execute keeps the contract simple and deterministic.
3. **Pin the snapshot once**: `GetOrBeginAsync(solutionId)` + a single `ReadModelAsync` (whole-batch `Indexing` while loading, identical to every other tool). If `expectSnapshot` was supplied and does not equal the pinned model's `Id`, stop here with whole-batch `error=Stale` — before any op runs, so a rejected continuation costs nothing. That failure carries a `snapshot=<current id>` header alongside `error=`/`errorMessage=` (the `candidate=` precedent), and names both ids in the message text (Decision 8). The public method delegates to an `internal ExecuteBatchAsync(SolutionModel pinnedModel, …)` overload — the seam that makes the stale-model pinning proof (Task 5) possible, and which also accepts a test-injected catalog for the throwing-core test.
4. **Execute sequentially in request order.** Each op invocation is wrapped in its own `try/catch` (shared mapper from B): a throwing core becomes that slot's `error=` block; the batch continues. Without this boundary one throwing core unwinds the whole call — the standalone path has the catch at the wrapper level (RoslynkTool.cs:42) but a batch must provide it per-op.
5. **Truncation** (Decisions 1 and 5, one code path): ops beyond index 25 are never executed, and execution stops early if accumulated output ≥ `MaxTotalOutputChars`. Every not-executed op still gets a numbered slot carrying a complete `error=Truncated` block naming why, and the envelope header gains `truncatedSlots=<n>`. No body is ever cut mid-output and there is no `truncated=Y` marker — a slot is either its whole real body or a whole error block, so the caller can resend exactly the truncated indices.
6. **Render** the envelope per the Proposed shape: `operations=<n>` + `snapshot=<32-hex>` + `boundary=<32-hex>` lines, then per slot `--<boundary>` / `slot=<i> tool=<name>` / blank line / body verbatim; finish with `--<boundary>--`. Then the belt-and-braces integrity check (Decision 2): the assembled envelope must contain the counted token `"\n--" + boundary` exactly `n+1` times — not the bare hex, which also appears in the `boundary=` header; otherwise fault the whole call with `error=Faulted`, because an envelope bug must never ship a silently desynced response. No envelope-level status (Decision 6).

Concurrency: multiple concurrent multi_query calls are safe — each pins its own immutable snapshot, reads are lock-free, writes serialize on the write channel, and the *next* call sees the post-write snapshot.

### D. The snapshot guarantee — absolute, no exceptions

The issue's criterion "results within one multi_query cannot disagree with each other" holds **without qualification**. All 11 catalogued ops receive the one `SolutionModel` captured at step 3 and can observe nothing else: `SolutionModel` is immutable, writes produce a new model rather than mutating this one, and no core acquires its own (Design A, enforced by the Task 3 assert). There is no second class of op, no `OpClass` enum, and nothing to caveat in the tool Description.

This is precisely what excluding `get_diagnostics` and `get_solution_status` buys (Scope decision 2). Both would have been documented exceptions to the headline guarantee — and a guarantee with exceptions is one an agent has to reason about per-slot rather than trust. The two remain ordinary single calls.

If either is ever admitted later, this section is where the exception must be written down, tagged in the catalog, and tested — not left as folklore.

**The guarantee is per call, and always was.** It says nothing about two multi_query calls, or a multi_query and a later single call: between calls the solution can advance, exactly as it can between any two Roslynk calls today. This matters most for a continued truncated batch, where a caller might reasonably assume otherwise — Decision 8's `snapshot=`/`expectSnapshot` pair exists precisely so that assumption is checked rather than trusted.

## Risks / tradeoffs

- ~~Reject-vs-truncate (>25 ops)~~ — **closed: truncate, author-confirmed** (Decision 1). This matches the issue's wording exactly — it asks for a maximum operation count that "reports truncation rather than silently dropping" — and matches the output budget, so both limits share one shape and one code path. The point is caller continuation: partial results plus an exact list of what to resend beats discarding a well-formed request. Do not reopen during implementation.
- **GUID framing (Decision 2, author's choice)**: skimmable and MIME-familiar; soundness rests on per-request freshness (`Guid.NewGuid()` v4, never reused) + the pinned snapshot, not collision odds; the occurrence check keeps envelope bugs loud. Two details that bit reviewers and must not be lost: the counted token is `"\n--" + boundary` (counting the bare hex would include the `boundary=` header and expect `n+2`), and delimiter handling must tolerate `\r\n` endings because source bodies carry `\r`.
- **Instruction-injection note on framing**: slot bodies are verbatim source, so a repository file *can* contain text shaped like a delimiter or meta line. The fresh-per-request boundary is what makes that inert. Treat the `n+1` check as a safety property, not a nicety — it is the thing that turns any future framing bug into a loud failure rather than a response an agent silently misparses.
- **Enum surface (Decisions 3–4)**: the enum is exactly the 11 permitted names, so the schema never advertises an op that will be refused — at the cost of one forbidden op failing the whole batch rather than one slot, and of deviating from the issue's `NotSupported` wording. The Task 3 name-set assert keeps enum and catalog in lockstep as tools are added.
- **Cross-call consistency (Decision 8)** is the one property multi_query cannot give: a continued batch spans two snapshots. `expectSnapshot` makes that detectable, not impossible. If experience shows agents continue often and hit `Stale` regularly, the next step is server-held resumable snapshots (a continuation token with a TTL) — deliberately out of v1, since it makes the tool stateful and pins Roslyn `Solution` graphs in memory past the call.
- **`SolutionModel.Id`** is the plan's only lifecycle change: one `init`-only `Guid` on an already-immutable type, no locking, nothing on the read path. Cheap, but it *is* a touch to shared infrastructure — keep it to that one line.
- **New `Error.Truncated` code** widens the public error surface by one. It now carries both truncation triggers (op count and output budget) and is a routine continuable outcome rather than a caller error, so it warrants its own code rather than reusing `Invalid`. Add it to the skill's error-code list in Task 6.
- **Reflective binder** trades ~50 generic lines for zero per-tool binder code; `MethodInfo.Invoke` is marginally slower per op than a direct call — irrelevant at batch scale (the op bodies themselves are the cost).
- **Excluded tools** (`get_diagnostics`, `get_solution_status`, `get_code_actions`, `open_solution`, `reload_solution`): each is one catalog entry plus an enum member if ever wanted, but the first two would also reintroduce documented exceptions to the Design D guarantee — that is the real cost, not the code.
- **Parallel ops within a batch** explicitly out of scope (YAGNI — the issue's motivation is round trips, not latency).
- **Task 7 harness** depends on whether stdio spawning is stable in CI; the in-process `RequestContext` fallback is named up front.
